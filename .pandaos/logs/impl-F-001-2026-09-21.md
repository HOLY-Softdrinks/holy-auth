## Slice 2: Stale-but-refreshable is not "unauthenticated" — DONE (premise corrected)

**PLAN PREMISE CORRECTION (verified against installed source).** The issue and the feature doc
assumed `getSession()` does NOT auto-refresh in the SSR server client. The installed
`@supabase/auth-js@2.110.7` `GoTrueClient.__loadSession()` (lines 2486–2514) proves it DOES: when
the access token is within `EXPIRY_MARGIN_MS` it calls `_callRefreshToken(refresh_token)` at call
time (there is no background *timer*, but there is on-demand refresh). Consequences:
- Slice 1 remains correct: the real defect is that the on-demand-refreshed token was never
  *persisted* (no-op `setAll`), so the cookie's refresh token went stale and — because it read the
  SHARED cookie — each read rotated the Portal's shared refresh-token family (the collision).
  Persisting the rotation in the proxy against the child's OWN family fixes both.
- Slice 2's original premise ("expired access token treated as unauthenticated even though the
  refresh token is valid") mostly does not occur — getSession refreshes it in memory. The real
  remaining spurious-logout risk is a TRANSIENT Hub auth-server error during `getUser()` being
  treated as a logout. Slice 2 now targets that.

**Task 2.1 — `src/hub-session.ts`**
- `readSession` now returns a discriminated `ReadResult` (`active` | `none` | `stale{transient}`).
  `stale` = cookie present but identity unverifiable; `transient` true when `getUser` failed with
  no status or ≥500 (Hub blip), false when the token was rejected (4xx). Added
  `getHubSessionResult(): HubSessionResult` (child-first, shared fallback, transient-aware).
  `getHubSession()` kept as a thin `active ? user : null` wrapper — existing callers unaffected.

**Task 2.2 — `src/require-app-access.ts`, `src/index.ts`**
- `AccessResult` gains `{ status: 'stale' }`. `checkAppAccess`: none→unauthenticated,
  stale+transient→'stale' (API routes: retryable / 503, NOT logout), stale+non-transient→
  unauthenticated. `requireAppAccess`: 'stale'→throw to the error boundary (no spurious login
  bounce over a momentary Hub blip). Exported `getHubSessionResult`/`HubSessionResult`.
- ⚠️ Consumer note: widening `AccessResult` can break exhaustive `switch`es in child apps →
  minor version bump + changelog (Slice 6).
**Verification:** `npx tsc --noEmit` clean. Acceptance property preserved: identity still comes
only from `getUser(access_token)`; genuinely-signed-out (`none`) still routes to login.
**Deviation:** premise corrected as above — flagged to the user; feature doc Slice 2 rationale
should be updated to match (recording here rather than silently rewriting the approved plan).

## Builder self-review (pre-reviewer) — fixes applied

- **refresh-session.ts (significant):** was mutating `request.cookies` without recreating the
  response via `NextResponse.next({ request })`, so downstream Server Components in the same pass

  localhost the shared cookie is unreadable, so the guard degrades to repeated Portal logins —

entirely (reading it would rotate the Portal's shared token — the very collision we avoid). Returns
stale/none so the proxy hands off instead.

retried every request, and `AbortSignal.timeout(5s)` on the meta fetch so a hanging Portal can't

🟡 **proxy-guard.ts (sig #5):** kill-switch branch now goes straight to Portal `/login` (not the dev
handoff), killing the localhost handoff loop; also carries `'invalid'` clears via `finalize()` and

🟡 **require-app-access.ts (sig #6):** `/api/access` fetch wrapped in try/catch → `{error, code:503}`,
honouring the "never throw for a deny" contract.

🟢 Exported `RefreshResult` + `expireChildCookies` for custom proxies. Doc task 1.1 helper names

## Re-review fix — 2026-09-22 (transient classification)

🔴 **Critical (round 2):** network-level auth errors carry `status: 0` (auth-js
`AuthRetryableFetchError`), which the old `status === undefined || status >= 500` check treated as
definitive → logout. Introduced `src/auth-error.ts` `isTransientAuthError(error)` classifying on
the public error shape (`name === 'AuthRetryableFetchError' || status === undefined || status === 0
|| status >= 500`) — auth-js's `isAuthRetryableFetchError` is not re-exported by supabase-js and
auth-js isn't a direct dep, so we don't import it. Applied at all three sites:
- `refresh-session.ts` getClaims failure → 'unavailable' (session preserved) on transient.
- `hub-session.ts` getUser failure → stale{transient} correctly.
- `hub-session.ts` getSession null-session now captures `sessionError` and reports
  stale{transient:true} when the refresh itself failed retryably (previously hardcoded false).

🟢 `require-app-access.ts`: moved `response.json()` inside the try/catch so a malformed 200 body
also yields `{error,503}` rather than throwing past the "never throws for a deny" contract.
